[#idna-limits]
== Limits

[#idna-limits-dns]
=== The DNS lengths

Under `verify_dns_length`, the default, a label is 1 to
`idna::max_label_length`, 63, octets in its ASCII form, and a name 1 to
`idna::max_domain_length`, 253, without a final root label, which is
refused: RFC{nbsp}1034 section 3.1's limits, as UTS{nbsp}46 section 4.2 states them. A
U-label is measured by its A-label: 55 `a` and a `ü` make an A-label of 63
octets, and 56 make one of 64.

[#idna-limits-storage]
=== The working storage

The conversions and the checks hold one label at a time, in a working
storage of 256 code points inside the call, about 1.3 KiB with the label's
ASCII form, and a second one while a label is checked for NFC the slow way.
Every label the DNS lengths accept fits: an A-label decodes to at most 59
code points, and a code point decomposes to at most 4, U+1FAF among them,
the longest canonical decomposition of Unicode {unicode-version}, which the
generator checks.

A label beyond 256 code points once decomposed is too long for the DNS, and
what meets it depends on the length check:

* Under `verify_dns_length`, `to_ascii`, in both forms, and the validators
  refuse it as `label_too_long`, which it is, as they refuse a label whose
  NFC check's copy outgrows the storage.
* Without it, the span form of `to_ascii` and the validators return
  `storage_exhausted`, and the pmr form of `to_ascii` takes the label's
  storage from its memory resource.
* `to_unicode` checks no label's or name's maximum length, and meets such a
  label with any options: its span form stops there with
  `storage_exhausted`, and its pmr form converts the label, an A-label
  within Punycode's bound (below). The difference is by design: a span form
  allocates nothing, and the label is no name the DNS can hold.

The storage fills while a label is gathered, before any of the label's
checks, so a label beyond it reports that first: U+FFFF followed by 300 `a`
is `label_too_long`, not `disallowed`. In the span form of `to_unicode`, the
processing stops there, keeping an error recorded before it, and its output
ends with the last label written before the long one: a name of the labels
`+a_b+`, 300 `a` and `c` gives `+a_b+`, and `not_ldh`.

[#idna-limits-punycode]
=== Punycode's bound

Punycode's work grows with the square of a label's length: RFC{nbsp}3492's
encoder passes over the label once for each distinct code point, and its
decoder inserts each code point among those before it. The conversions bound
it at 256 code points, the working storage's, and Punycode past the bound is
`punycode_overflow` whatever `ignore_invalid_punycode` says, since a limit of
the implementation is no invalid Punycode. `to_ascii` encodes, so a label of
more than 256 code points that is not ASCII is `punycode_overflow` there.
Both conversions decode, so an A-label whose Punycode decodes to more than
256 code points is `punycode_overflow` in either, and kept as it is in the
Unicode form. `to_unicode` encodes nothing: a long label that is not an
A-label is written as it is. Only a pmr form meets the bound, `to_ascii`
without the DNS lengths, and `to_unicode`, with any options, for an A-label,
since a span form refuses such a label as beyond its storage first. At the
bound, the worst label costs about 4 times one as long that Punycode handles
in linear time, measured at `-O2`.

`punycode::encode` and `punycode::decode` are the primitive, and have no
such bound: their pmr forms take input of any length, in time that grows
with its square, and their span forms stop when the caller's span is full,
in time that grows at most with the input's length times the span's size. A
program bounds the length of input it does not trust before it hands it to
a pmr form.

[#idna-limits-stack]
=== The stack

The deepest call of idna, a check of a label, or a conversion of an
A-label, whose U-label holds more than 32 combining marks in a row, which the
slow NFC check sorts by counting, ran in about 11 KiB of stack, and the
conversions and checks of an ordinary name, such as
`+xn--bcher-kva.example+`, in about 8 KiB, a program's start and its `printf`
included, against the 64 KiB a WebAssembly program gets by default. These
are measured figures, with no margin promised: a program built with
wasi-sdk 34 in a debug build (`-O0 -g`) for wasm32-wasip2 and wasm32-wasip3,
run by wasmtime 47 with a stack made smaller, 256 bytes at a time, until it
trapped. Another compiler or version may need more. idna does not
recurse.
